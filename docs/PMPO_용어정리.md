# PMPO 프로젝트 용어 정리

> PM/PO로 일하면서 마주칠 실무 용어와 이 프로젝트에서 쓰인 용어들을 정리한 문서입니다.
> Claude Code에게 주는 개발 프롬프트에는 넣지 않고, 여기서만 계속 업데이트합니다.
> 새 대화에서 새 용어가 나올 때마다 이 문서에 계속 추가해주세요.

---

## 기획/문서 관련

| 용어 | 설명 | 어디서 나왔는지 |
|---|---|---|
| **PRD** (Product Requirements Document) | 제품 요구사항 정의서. 문제정의·타겟유저·핵심기능·성공지표 등을 정리한 기획의 뼈대 문서 | PMPO PRD v0.5 작성 단계 |
| **IA** (Information Architecture, 정보구조) | 서비스 안의 메뉴/화면들이 어떻게 나뉘고 연결되는지 짜는 설계. 사이트맵이 대표적 산출물 | IA v0.2 확정 단계 |
| **와이어프레임(Wireframe)** | 디자인(색·폰트) 없이 화면의 배치와 기능만 표현한 저해상도 설계도 | 화면설계 v0.7 단계 |
| **MVP** (Minimum Viable Product) | 검증에 필요한 최소한의 기능만 담은 첫 출시 버전 | UI디자인시스템 문서에서 "MVP 속도 우선" 언급 |
| **MoSCoW** | 기능 우선순위를 Must-have(필수)/Should-have/Could-have/Won't-have로 나누는 방법 | 프로젝트 전반의 기능 우선순위 정리 방식 |
| **오픈 질문(Open Question)** | 아직 결론 내지 못하고 열어둔 이슈. PRD 등 문서에 별도 섹션으로 기록해 나중에 재검토 | PRD "오픈 질문" 섹션 |
| **백로그(Backlog)** | 지금 버전엔 넣지 않지만 다음 버전에서 고려할 기능/작업 목록 | PRD·IA 문서의 "백로그" 섹션 |

## 유저 리서치/검증 관련

| 용어 | 설명 | 어디서 나왔는지 |
|---|---|---|
| **페르소나(Persona)** | 실제 유저를 대표하는 가상의 인물상. "주니어 PM", "PM 취업 희망자" 등으로 구체화해 기획 기준으로 삼음 | PRD 타겟 유저 정의 |
| **유저 플로우(User Flow)** | 유저가 서비스에 들어와서 목표를 달성하기까지 거치는 화면·행동의 순서 | IA v0.2 "페르소나별 유저 플로우" |
| **이탈률(Retention/Churn)** | 유저가 서비스를 떠나는 비율. 낮을수록 계속 남아있다는 뜻 | 카카오톡 채널 6개월 운영 검증 단계 |

## 지표 관련

| 용어 | 설명 | 어디서 나왔는지 |
|---|---|---|
| **바이너리 메트릭(Vanity Metric)** | 보기엔 좋아 보이지만 실제 성과와 직결 안 되는 지표 (글/댓글 개수, 조회수 등) | PRD 성공지표를 "글 개수"에서 "답변률"로 교정한 배경 |
| **행동 지표(Behavioral Metric)** | 유저의 실제 행동을 반영해 서비스 목적과 직결되는 지표 (답변률, 응답시간 등) | PMPO 핵심 원칙 — vanity metric 대신 이걸 우선함 |

## 개발/기술 관련 (알아두면 좋은 수준으로 쉽게)

| 용어 | 설명 | 어디서 나왔는지 |
|---|---|---|
| **RLS** (Row Level Security) | 데이터베이스에서 "누가 어떤 데이터를 보고 고칠 수 있는지"를 행(row) 단위로 제한하는 보안 규칙. 예: 본인 글만 수정 가능하게 막는 것 | 개발 단계 — RLS 정책 전체 테이블 적용, 보안 구멍 발견/수정 |
| **CRUD** | Create(생성)·Read(조회)·Update(수정)·Delete(삭제). 데이터를 다루는 가장 기본적인 4가지 동작 | 게시글 CRUD 구현 단계 |
| **Auth** (Authentication) | 로그인/회원가입 등 "이 사람이 누구인지 확인하는" 인증 기능 | Supabase Auth 로그인 연동 |
| **매직링크(Magic Link)** | 비밀번호 없이 이메일로 받은 링크 클릭만으로 로그인하는 방식 | 초기엔 매직링크였다가 이메일+비밀번호 방식으로 전환 |
| **git push / pull** | push는 내 컴퓨터의 작업 내용을 온라인 저장소(GitHub 등)에 올리는 것, pull은 반대로 받아오는 것. 여러 기기를 오가며 작업할 때 필수 | iCloud 폴더 이동 사고, 기기 전환 워크플로우 |
| **DNS 전파(Propagation)** | 도메인 주소 변경 설정이 전 세계 서버에 반영되기까지 걸리는 시간(보통 몇 시간~하루) | 도메인 연결 단계 |
| **네임서버(Nameserver)** | 도메인 이름을 실제 서버 주소로 연결해주는 시스템. 이걸 옮기면 도메인 관리 권한 자체가 이전됨 | 아임웹→Vercel 네임서버 이전 |
| **A레코드** | 도메인을 특정 IP 주소로 직접 연결하는 설정 방식(네임서버 이전과는 다른, 더 부분적인 방법) | 아임웹의 A레코드 제한 정책으로 네임서버 이전 방식 선택 |

## 디자인/UI 관련

| 용어 | 설명 | 어디서 나왔는지 |
|---|---|---|
| **디자인 토큰(Design Token)** | 색상·폰트 크기·여백 같은 디자인 값들을 코드에서 재사용하기 쉽게 이름 붙여놓은 변수 (예: `--accent: #C8464D`) | 컬러 시스템 v1.0/v1.1 문서 |
| **CTA** (Call To Action) | "글쓰기", "질문하기"처럼 유저의 행동을 유도하는 버튼/문구 | 톤앤보이스 가이드, 버튼 컬러 규칙 |
| **Hover / Pressed 상태** | Hover는 마우스를 올렸을 때, Pressed는 클릭하는 순간의 시각적 상태 변화 | 버튼 색상 규칙 정의 |
| **칩(Chip)** | 배경색이 채워진 알약 모양의 작은 라벨 UI (태그, 상태 표시 등에 흔히 씀) | 컬러 시스템 v1.1 — "배경 채운 칩 대신 아이콘/텍스트로만" 절충 |
| **뱃지(Badge)** | 특정 조건(팔로워 수 등)을 달성하면 부여되는 인증/성취 표시 | PRD "우수 답변 및 팔로우 수 보상 장치" — 팔로우 30명 이상 |
| **반응형(Responsive)** | 화면 크기(모바일/데스크톱)에 따라 레이아웃이 자동으로 달라지는 디자인 방식 | 와이어프레임은 모바일 우선 설계 + 데스크톱 레이아웃 별도 작업 |
| **에디토리얼(Editorial) 디자인** | 잡지·매거진처럼 텍스트 위계와 여백으로 구조를 만드는, 장식이 적은 디자인 스타일 | 컬러 시스템 v1.1 — Asterisk, Works in Progress 레퍼런스 |
| **접근성(Accessibility)** | 색약, 저시력 등 다양한 사용자도 문제없이 쓸 수 있게 만드는 디자인 원칙. 색만으로 정보 전달하지 않는 것도 여기 포함 | 톤앤보이스/컬러 시스템 — "색상만으로 상태 전달하지 않는다" 원칙 |
